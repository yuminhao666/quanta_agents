# News Event Pipeline Audit

This audit is the Phase 0 baseline for the news-data chain sidecar. It only covers
news flashes and the existing `opinion_radar` / `news_logic` path; research-report
Atomic Claims, Neo4j, platform UI contracts, and gold promotion are out of scope.

## Current News Input

- Runtime input is MySQL through `quanta_agents.opinion_radar.db`.
- Default table is `jin10_flash`, configurable with `RADAR_FLASH_TABLE`.
- Connection envs are `RADAR_MYSQL_*`, then `MYSQL_*`, then `GJ_FUTURES_MYSQL_*`.
- `fetch_flashes(start, end)` reads the rolling or daily window used by
  `opinion_radar.service`, `opinion_radar.export`, and `opinion_radar.news_logic`.

## MySQL Table Fields Used Today

`opinion_radar.db.fetch_flashes` selects only:

```sql
SELECT id, flash_id, publish_time, important, channel, title, content, url
FROM jin10_flash
WHERE publish_time >= %s AND publish_time < %s
ORDER BY publish_time ASC
```

Observed runtime assumptions:

- `publish_time` is converted to a string with second precision when returned.
- `important` is coerced to `int`.
- `id` and `flash_id` are both treated as possible stable source row IDs.
- No current query reads source name, ingestion time, author, canonical URL, or
  upstream duplicate metadata.

## Current Filtering Logic

`opinion_radar.filters.keep_flash` keeps a flash when:

- the joined title/content contains a signal keyword such as data release,
  inventory, policy, sanction, production, shutdown, conflict, blockade, strike,
  emergency, and similar market-relevant terms;
- or `important` is truthy;
- otherwise it filters pure market-move text detected by price-move and percent
  regexes.

Limitations:

- The decision is boolean only; it does not preserve `filtered_out`, `candidate`,
  `relevant`, `priority`, or reason codes.
- Filtered items are silently dropped in the downstream logic.
- Market observations can still be retained when they contain signal keywords,
  but there is no separate event-stage or truth-status classification.

## Current News To Asset And Framework Path

The existing chain is:

```text
MySQL jin10_flash
  -> filters.keep_flash
  -> news_logic._display_text / _flash_time / _flash_key
  -> load_asset_taxonomy(...).classify(text)
  -> one mapped row per variety hit
  -> load_framework_for_asset(asset)
  -> iter_leaf_nodes(framework)
  -> futures_daily.framework_alignment._match_framework_node
  -> _consistency against latest trade_thesis + dimension_scores
  -> build_news_logic_radar assets/dimensions/events
  -> optional LLM asset-level assessment
  -> opinion_radar reports
```

The important behavioral detail is that `map_flash_to_events` creates one
`NLOGIC-*` event per matched asset/framework node. Therefore one real-world news
event affecting oil, gold, and copper is currently represented as three asset
events. Those rows are useful for the old `news_logic` contract but are not a
canonical real-world event model.

## Current Theme Anchor Use

`signal_mapping.theme_anchor_matcher.load_theme_anchor_index` prefers:

1. an explicit `--theme-anchor-path`;
2. the object catalog persistent-topic registry when
   `QUANTA_OBJECT_CATALOG_ENABLED=true` and the catalog SQLite exists;
3. otherwise the latest candidate files under
   `agent_workspace/candidates/theme_anchor/*/*/*/CAND-THEME-ANCHOR-*/theme_anchors.json`.

Default candidate loading is capped to the latest three files. This means the
normal unconfigured path is still recent-candidate oriented, not a dedicated
long-lived news topic registry.

## Current Outputs

The existing platform-facing outputs are:

```text
agent_workspace/candidates/opinion_radar/latest/radar.json
agent_workspace/candidates/opinion_radar/{yyyy}/{mm}/{dd}/radar-{HHMMSS}.json
agent_workspace/candidates/opinion_radar/news_logic/latest/news-logic.json
agent_workspace/candidates/opinion_radar/news_logic/{yyyy}/{mm}/{dd}/news-logic-{HHMMSS}.json
agent_workspace/candidates/opinion_radar/reports/latest/market-radar-report.json
agent_workspace/candidates/opinion_radar/reports/latest/market-radar-report.md
agent_workspace/candidates/opinion_radar/reports/{yyyy}/{mm}/{dd}/market-radar-report-{HHMMSS}.json
agent_workspace/candidates/opinion_radar/reports/{yyyy}/{mm}/{dd}/market-radar-report-{HHMMSS}.md
```

`news_logic` also currently appends a lightweight in-memory sidecar generated by
`knowledge_fabric.build_news_event_sidecar`:

- `event_mentions`
- `canonical_events`
- `persistent_topics`
- `topic_memberships`

That sidecar groups by legacy `flash_id` after asset mapping. It is not the new
SQLite news-event catalog, does not perform mention extraction before asset
mapping, and does not model syndication or event relations.

## Compatibility Contracts To Keep Unchanged

The following must remain readable with their current shapes:

- `news_logic_radar.v1` top-level fields:
  `schema_version`, `status`, `generated_at`, `logic_context`,
  `analysis_framework_ref`, `theme_anchor_context`, `semantic_layer`, `stats`,
  `assets`, `events`.
- Legacy event rows with `event_id`, `flash_id`, `asset`, `asset_id`,
  `publish_time`, `text`, `url`, `channel`, `important`, `direction_score`,
  `heat`, `framework`, `framework_node`, `match`, `theme_anchor_refs`,
  `anchoring_status`, and `consistency`.
- `opinion_radar.v1` `radar.json` windows, timeline, health, and embedded
  `news_logic` refs.
- `market-radar-report.{json,md}` reading from old radar/news_logic payloads.
- Candidate/review semantics: all outputs remain `candidate`, reviewable,
  traceable, and do not write to `gold`.

## Minimum Non-Breaking Implementation Plan

Add a new `quanta_agents.news_events` sidecar pipeline:

1. Normalize raw MySQL rows into stable `NewsItem` objects before asset mapping.
2. Preserve filter decisions and reason codes instead of silently dropping items.
3. Build exact/near duplicate and syndication groups before event extraction.
4. Extract `EventMention` using LLM when available and deterministic fallback
   when not.
5. Persist `CanonicalEvent`, event membership, relations, asset links,
   framework-node links, persistent topics, and topic memberships in a separate
   SQLite catalog under `indexes/news_event_catalog/news_events.sqlite3`.
6. Generate the requested sidecar JSONL run directory under
   `agent_workspace/candidates/news_events/{yyyy}/{mm}/{dd}/RUN-.../`.
7. Generate a compatibility view from canonical events plus links for old
   `news_logic` consumers, without replacing the existing `opinion_radar`
   runtime by default.
8. Gate old-pipeline integration with `QUANTA_NEWS_EVENT_PIPELINE_ENABLED`.

This keeps the old `opinion_radar` behavior unchanged when the flag is off, while
making the new real-world event layer independently runnable, testable, and
idempotent.
